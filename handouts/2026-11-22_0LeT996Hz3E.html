Engineer Your Coding Agents Like Any Other System — Zach Lloyd, Warp

AI Engineer · 18 min talk · Watch · Transcript · 2026-11-22 23:53 UTC · gemini-3.6-flash

Coding agents are a new engineering primitive: engineer them as a code-defined, closed-loop factory, because local interactive use caps throughput, blocks cost and quality control, and escapes governance.

TL;DR

  • A software factory is a code-defined, closed-loop system for continuously measuring and improving cloud coding agents — not automations, teammates, or shared skill collections.
  • Centralization paid for Warp: 40% more merged PRs and 67% lower cost per merged PR, roughly $55 to $18 between September and October 2025.
  • Decide model and factory choices by measuring your own data: online evals across all sessions, plus benchmarks like WarpBench 0.1 distilled from real runs.
  • Self-improvement closes the loop — agents read scorer outputs and propose fixes as PRs — with human approval as the gate.

Talk by Zach Lloyd, founder and CEO of Warp (previously principal engineer at Google, led Google Docs engineering), at AI Engineer Code Summit. Warp sells a platform for building internal software factories; its open-source agentic terminal has about 65,000 GitHub stars and almost a million developer users. All evidence shown is from Warp's own internal factory, eng-factory-slim, demonstrated on a staging platform — a vendor presenting its own product.

Deep dives

[03:37] What a software factory is — and is not

  • Not a loose automation set, AI teammates, a shared skills-and-MCP setup, or a personal agent swarm — useful primitives, not the end state.
  • Encode the factory declaratively, Terraform-style: agents, triggers, triage-to-spec workflow, available MCPs, where agents run — demoed as one factory.yml.
  • The loop is the SDLC with human review gates at spec, code, and product; more agent runs let you improve loop efficiency.

Why it matters: Gives a binary maturity test: without code-defined config and a measurement loop, an agent deployment is not a factory. (inference)

Watch out: Continuously measuring and improving sets no operational bar; how much measurement suffices is left undefined.

[08:06] The factories stack

  • Seven layers, 00 to 06, bottom-up: factories-as-code, data and context, compute, inference, improvement, orchestration, access.
  • Data and context: runs, transcripts, agent artifacts, MCPs and internal knowledge, access control; compute: sandboxing, agent runner, compute size.
  • Inference is multi-model with bring-your-own-model and a custom router; the whole factory is API and MCP first.

Why it matters: A scoping template: each layer is a gap-analysis dimension and a build-or-buy decision for any agent deployment. (inference)

Watch out: One vendor's first-principles sketch; the speaker says it does not have to be exactly this.

[13:24] Scorers and self-improvement: closing the loop

  • Online evals run across all coding-agent sessions; a Redundant Tests scorer checks delivered test diffs for low-signal or trivial tests.
  • Self-improvement: instead of humans reviewing scorer outputs, agents review them and open PRs proposing fixes to their own skills.
  • Factory-as-code enables this: agents can diagnose problems with how they work and suggest fixes to their own configuration.

Why it matters: Eval signal compounds into configuration changes while humans stay as approvers — automated quality control with an audit trail. (inference)

Watch out: Scorers are prompts that can misclassify; self-improvement can then write those errors into skill configs unless approvals catch them.

Field playbook (inferred from the talk, not claims made in it)

Ask the customer

  • How are coding agents configured and triggered today — individual local setups or shared definitions in code?
  • What per-PR and per-run cost and quality data do you already collect, and who reviews it?
  • Where do agent runs execute, and what sandboxing, access control, and audit trail exists?

Measure in a pilot

  • Human interactions per PR and median kickoff-to-PR and kickoff-to-merge cycle time, baselined before rollout.
  • Cost per PR, total spend, and most expensive PRs, broken out by model.
  • Scorer pass rates for your own failure modes, plus the scorers' answer cost.

Where it breaks

  • Engineers bypass the central factory with local agents, splitting data, cost visibility, and governance.
  • Prompt-based scorers misclassify outputs; self-improvement then writes the errors into skill configs.
  • Self-improvement proposals overwhelm human approvers, making review the throughput bottleneck.

What the talk does not establish

  • No control group behind the throughput, review-rate, and cost changes; before/after windows invite confounding.
  • The PR review rate metric is undefined; what the percentage counts is unclear in transcript.
  • Neither benchmark states N or evaluation window; some costs are approximate, read from a scatter plot.
  • All results come from Warp's own team and codebase; nothing is replicated externally or at a customer.

Checklist

  • Define your agent estate declaratively in versioned config: agents, triggers, workflow, MCPs, run locations. [03:55]
  • Centralize runs, transcripts, and artifacts so every agent session is inspectable team-wide. [11:34]
  • Stand up online evals with named scorers covering every coding-agent session. [13:24]
  • Create benchmarks from your own real tasks and A/B test models and factory changes on them. [16:05]
  • Wire self-improvement: route scorer findings to agents that draft fix PRs, gated by human approval. [14:58]
