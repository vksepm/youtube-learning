What it takes to set intelligence free — Fabian Hedin, CTO, Lovable

AI Engineer · 22 min talk · Watch · Transcript · 2026-11-23 02:17 UTC · gemini-3.6-flash

Now that model intelligence has arrived, agents can run for hours, provided the platform supplies a persistent task history, resumable sandbox computers, and verification feedback loops.

TL;DR

  • Multi-agent orchestration nearly sank Lovable in 2023; it works now because model intelligence, not framework design, finally arrived.
  • Hour-long-plus agent runs rest on three systems: an inbox-driven runtime over durable task history, resumable sandbox snapshots, and two verification loops.
  • Because task history lives outside stateless processes, one long task keeps going while processes swap underneath during routine deploys.
  • Dropping the Node.js runtime under Vite, rewritten in Rust as OJ, multiplied how many agent previews fit per machine.

Talk by Fabian Hedin, co-founder and CTO of Lovable, at the AI Engineer Code Summit (presented by Google DeepMind). Lovable builds, runs, and deploys software from a chat-plus-preview interface, with agents processing billions of tokens per minute in production. All evidence is this single vendor's self-reported telemetry and internal benchmarks: no sample sizes, methodology, or third-party comparisons, and the closing multi-agent picture is aspirational, not measured.

Deep dives

[08:51] Agent runtime: inbox, append-only history, rebuilt prompts

  • A per-agent inbox takes messages from you, other agents, or scheduled wake-ups; the control plane starts agents and wakes one on arrival.
  • The agent copies inbox messages into its trajectory between steps; the trajectory is an append-only log where each event points to a parent.
  • Forks share the parent and copy nothing; unlike Git, trajectories cannot merge. Every prompt is rebuilt from history, earlier steps summarized, recent steps in full.

Why it matters: Durable forking history makes runs auditable and restartable from the record; treating the log as the single source of truth is the transferable pattern. (inference)

Watch out: Forks cannot merge; summarized earlier steps lose detail the model may later need.

[14:56] Checkpointed sandbox computers and drafts

  • A golden checkpoint, OS, system services, common tools, dev server ready, is prepared once and copied into every new project computer.
  • At the end of every agent turn the running computer, files, memory, running processes, is snapshotted, then resumed in place.
  • Drafts fork one snapshot into parallel computers; copy-on-write copies RAM pages only on write, and memory streams in so the machine boots before all pages arrive.

Why it matters: Snapshots make sandbox state cheap to clone, resume, and explore in parallel; the substrate behind drafts and unbounded run time. (inference)

Watch out: Each sandbox needs hundreds of MB of memory; fork count drives cost even with copy-on-write.

[18:05] OJ: Vite rewritten in Rust

  • Vite was forked and rewritten in Rust as one binary that runs the app the way Vite does, with no Node.js underneath.
  • Every preview runs a real dev server; the project is open source at github.com/lovable-dev/oj.
  • Dropping Node.js cut the memory footprint, letting lots of agents run in parallel on the same machines.

Why it matters: A shared runtime dependency, not the model, set the density ceiling; rewriting one component multiplies fleet capacity. (inference)

Watch out: Single-vendor internal benchmark with no external comparison.

[19:30] Verification: inner and outer loops

  • Inner loop during the turn: build, lint and type errors, runtime errors, judges, guardrails and notifications are automatic; browser checks, domain scanners and backend logs arrive via tools.
  • Outer loop between turns: production signals, visitor behaviour, automatic A/B tests, transactions to conversions, and what users explicitly report.
  • Feedback is fed back as next-turn findings; production outcomes never reach the agent as a training signal.

Why it matters: Keeps long runs self-correcting while separating evaluation from training, a clean governance boundary for regulated settings. (inference)

Watch out: The horizon between turns is long; production failures surface only at the next wake-up.

Field playbook (inferred from the talk, not claims made in it)

Ask the customer

  • What agent run duration do we need, and what deploy or restart cadence would interrupt it today?
  • Which verification signals exist automatically today, and which need tools or user reports?
  • Where does agent state live now, and could another process resume a stopped run?
  • What per-run compute and memory budget exists for sandboxed agent work?

Measure in a pilot

  • Share of agent errors caught and fixed within the turn.
  • Sandbox cold-start and resume latency, plus memory per sandbox.
  • Tasks resuming correctly after a deploy or process restart.

Where it breaks

  • Sandbox snapshots and forks accumulate storage and memory cost across long, parallel runs.
  • Outer-loop findings arrive only at the next scheduled wake-up, delaying reaction to production failures.
  • Compaction summarizes away earlier detail, causing repeated work across forks that cannot merge.

What the talk does not establish

  • No task success rates, verification pass rates, or completion metrics for agent runs.
  • No cost per sandbox, per token, or per long run.
  • All benchmarks are internal; no cross-vendor or third-party comparison.
  • Closing multi-agent vision shown as a concept without measured results.

Checklist

  • Externalize agent state into an append-only, forking event log; make worker processes stateless between steps. [13:05]
  • Add a per-agent inbox fed by users, other agents, and scheduled wake-ups that wakes the agent. [08:51]
  • Prepare a golden VM checkpoint with OS, tools, and dev server ready; measure its resume latency. [14:56]
  • Snapshot each sandbox at end of turn and resume it in place instead of rebuilding. [15:45]
  • Wire two verification loops and route production findings to the next turn, never to training. [19:30]
  • Benchmark dev-server memory and preview startup with the Node runtime removed before any rewrite. [18:35]
